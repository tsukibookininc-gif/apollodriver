# Twin X USB: подготовка отдельного RAM boot эксперимента

Обновлено 17 ноября 2026. **До отдельного согласия владельца запускать режим
записи нельзя.** Это не готовый аудиодрайвер. Обнаружение runtime PID после
эксперимента не подтвердит DSP, звук или совместимость с UAD Console.

## Что проверено на присланном файле в облаке

Файл получен от владельца из его установленной официальной Windows UAD-копии.
Сам файл, исполняемый код прошивки и содержимое секций не публикуются в GitHub
и не входят в CI/artifacts. Ни одна из проверок ниже не запускала эту прошивку.

- ApolloTwinX.bin: 147416 байт, SHA256
  `bdd9db3f2d139f615c4f1e4e0261d24d90a6f95f8c6e1afe34e0c1a8fbd35fcc`.
  Совпадает с upstream pin UAD 12.0.0.602; это сопоставление известного файла,
  а не цифровая подпись UA или доказательство его поведения при выполнении.
- CY header: `43 59 1c b0`. Стандартный B0 checksum image, executable bit0 = 0.
- Четыре секции, длины в 32-битных little-endian словах. Смещения ниже — байты
  от начала файла; диапазоны RAM указаны с исключённым правым концом.

| Смещение данных | Диапазон памяти | Длина |
| --- | --- | --- |
| 12 | 00000100–00002328 | 8744 |
| 8764 | 40003000–40013000 | 65536 |
| 74308 | 40013000–4001F30C | 49932 |
| 124248 | 40030000–40035A74 | 23156 |

Сумма payload words modulo 2^32: `28D1A1F1`, совпадает с последним словом файла.
Entry point: `40011820`, внутри загружаемой секции. Все секции выровнены,
не перекрываются и находятся в ITCM или консервативном 256 KiB SRAM envelope;
область bootloader/descriptor RAM исключена. Наличие конкретной FX3-ревизии
в Apollo не установлено по маркировке чипа; это проверка карты адресов образа.

Предыдущее вложение ApolloTwin.bin было другим файлом: 147448 байт,
SHA256 `80ad9882af817d574a9fb5df2ac27f70e2d3b4e6947d738e08f8446367614da1`,
совпадающим с upstream Twin USB pin. Такой файл отвергается даже после переименования.

## Подготовленный код

`apollo-inspect` сохраняет режимы диагностики. Отдельный `apollo-boot` по умолчанию
читает файл, проверяет CY/B0 структуру, адреса, trailer/checksum и SHA256, печатает
план и **вообще не обращается к USB**. Он не сохраняет отчёт автоматически:

```sh
./apollo-boot --image /path/to/your/ApolloTwinX.bin --plan
```

Путь — пример, его нужно заменить. Exit 0 означает только корректный план для
закреплённого Twin X image; exit 2 — разобранный, но не закреплённый образ; exit 1 —
ошибка аргументов, чтения или разбора. Реальная загрузка под Linux отсутствует.

Загрузчик отделён в собственный artifact `apollo-boot-macos-…-ARM64`. Он содержит
бинарник, эту инструкцию, LICENSE, BUILDINFO.json и SHA256SUMS. Firmware внутри нет.
LICENSE также сохраняет MIT notice для portable SHA backend.
CommonCrypto используется на macOS; Linux offline build использует vendored
PicoSHA2 (MIT), без дополнительных установок.
Подпись ad-hoc, без Developer ID/notarization. При блокировке следует сообщить
точный текст; изменение Gatekeeper/SIP/boot security, quarantine и sudo не нужны.

## Конкретная операция, требующая отдельного согласия

Режим `--execute` требует одновременно `--image`, явного `--location` и
`--confirm-twin-x-ram-boot`, несовместим с `--plan`. До открытия устройства файл
целиком считывается в ограниченный buffer и повторно проверяется по SHA256/pin.
Имя файла не служит доказательством модели. Затем:

1. Найти ровно один loader 2b5a:000e по указанному текущему location. Runtime на
   этом location, неоднозначность и неизвестная идентичность означают отказ.
2. Открыть device без seize; повторно проверить VID/PID/location. Нет detach,
   reset, SetConfiguration, SetAlternateInterface или системных установок.
3. Для этого образа отправить **38 RAM data writes**, всего 147368 байт,
   кусками до 4096 байт, запросы 40/A0. После каждого выполнить C0/A0 readback
   тех же адресов и сравнить все байты. Длины должны совпадать точно.
4. Только после всех 38 проверок — один zero-length 40/A0 jump к 40011820.
   Первая ошибка, short reply или несовпадение останавливает последовательность;
   повторов и продолжения после частичного сбоя нет.
5. После попытки jump — до 10 секунд только IORegistry observation. Успех этой
   ступени требует нового registry identity с 2b5a:000f по тому же location.
   ACK запроса, сам факт отправки и exit 0 без runtime не считаются успехом.

Jump может оборвать USB до ACK; такая ошибка сохраняется в отчёте. Она не
игнорируется: определить результат может только наблюдаемый runtime. При смене
location во время USB re-enumeration проверка консервативно не подтвердит результат;
нужен отдельный обычный `apollo-inspect`, а не автоматический поиск замены карты.

IOKit transfer timeout: 1 s no-data / 1.5 s completion. Прерывание процесса или
отключение карты посреди операции может оставить частично заполненную RAM. Код
hardware-записи и readback пока не выполнялся на Twin X; fake transport tests
не подтверждают USB transfers, boot firmware или звук.

## Последствия и план восстановления

Host-команды ограничены ITCM/SRAM и jump; EEPROM/SPI flash programmer, DSP init,
clock/routing writes и дополнительные vendor commands отсутствуют. Но после jump
исполняется оригинальный бинарный код UA: все его обращения к периферии не
проаудированы. Поэтому гарантировать отсутствие побочных эффектов или зависания
устройства по одному файлу нельзя.

Если эксперимент зависнет/не подтвердит runtime: прекратить запросы, выключить
Apollo, отсоединить USB, оставить питание выключенным на 10 секунд, затем включить
и подключить к Mac для обычного `apollo-inspect`. Ожидается возврат к исходному
loader 000E после потери volatile RAM. Этот способ восстановления соответствует
RAM boot модели FX3, но именно после нашего эксперимента на этой карте ещё не
проверен. Если исходное состояние не вернулось — остановиться и сохранить только
диагностику; неизвестные recovery/flash-команды не предлагаются.

Для удаления утилиты достаточно удалить её папку/архив. Системных установок нет.
Ни RAM boot, ни наблюдаемый PID 000F не устанавливают аудиодрайвер macOS.
