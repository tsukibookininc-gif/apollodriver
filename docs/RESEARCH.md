# Отчёт: первая облачная итерация

Обновлено 17 ноября 2026. Целевая модель: **Apollo Twin X USB**, MacBook Pro M5.
Репозиторий: `tsukibookininc-gif/apollodriver`. Разработка агента ведётся в облаке.
Владелец самостоятельно скачал утилиту и выполнил default scan, SHA256SUMS и cached
descriptor scan; системные компоненты проекта не устанавливались.
Владелец уточнил, что **до этого проекта самостоятельно** установил официальный
macOS-драйвер и UAD Console, но карта в них не определялась. Теперь в USB подтверждены
loader 2b5a:000e/WestBridge и 18-байтная vendor-only конфигурация без дополнительных
endpoints. Поле macos в выводе — 27.2.1, отдельно не сверено. Сырые наблюдения,
ограничения и проверка роли регистрации: [DETECTION.md](DETECTION.md).

## Что установлено

Публикации open-apollo дают существенную базу протокола, но не рабочий драйвер
Twin X USB для macOS. Сам README отмечает модель как требующую проверки. Есть
сообщения о звуке у Solo USB и Twin USB под Linux, однако перенос этих результатов
на Twin X USB и macOS не подтверждён. В отчёте владельца **Twin X USB** обнаружение
работает, а DSP init зависает. Все утверждения upstream остаются утверждениями
авторов/владельцев, пока мы не воспроизведём их на нужной карте. [Источники](SOURCES.md).

Протокол разделяется на несколько независимых слоёв:

1. **FX3 boot:** Twin X ожидается как `2b5a:000e`. Upstream отправляет сегменты
   принадлежащего пользователю boot image запросом 0xA0 по адресам памяти FX3,
   затем передаёт управление entry point. Это запись в устройство; здесь она не выполняется.
2. **Runtime USB identity:** ожидается `2b5a:000f`. Наличие такого PID означает
   только перечисление runtime USB; DSP, аудиомаршрутизация и звук ещё не доказаны.
3. **Vendor control:** интерфейс 0, запросы IN с type C1. Известны protocol word,
   версии FX3, status block, чтение FPGA-регистров. Это реализованный первый транспорт.
4. **DSP/routing:** bulk OUT/IN в upstream, модельные DSP-модули, команды соединения,
   загрузки, маршрутизации и подтверждения. Solo-последовательность может зависать на
   Twin. Мы её не переносим и не выдаём отправку всех пакетов за успешный init.
5. **Audio:** отдельные UAC2 AudioStreaming-интерфейсы, изохронные endpoints,
   alternate settings, частота и clock feedback. Адреса/форматы должны прийти из
   дескрипторов **этого** Twin X, а не из таблицы Solo или другого Twin.

Таблица известных IN-запросов, реализованных только для runtime PID 000F:

| Назначение | bmRequestType / bRequest | wValue / wIndex | Размер |
| --- | --- | --- | --- |
| Protocol | C1 / 00 | 0 / 0 | 4 |
| Status | C1 / 06 | 0 / 0 | 36 |
| Version A | C1 / 0E | 0 / 0 | 4 |
| Version B | C1 / 0F | 0 / 0 | 4 |
| DSP0 boot word | C1 / 04 | 1069 / 0 | 4 |

Для status проверяется magic `0x2a2b4b4a`. Остальные неизвестные поля сохраняются
как числа, без выдуманных значений. Boot word не равен нулю/`f81a3c5e` и bit0
установлен — это upstream-правило готовности DSP, **не доказательство аудио**.
При первой ошибке/неполном ответе новые запросы прекращаются. Повторов, reset,
clear halt, scan регистров или неизвестных команд нет. IN-запросы известны из
анализа upstream, но на Twin X под macOS ещё не проверены.

## Что реализовано в этом репозитории

Нативный C++17 driver research transport через IOKit/IOUSBLib, без libusb и без
ядерного модуля. По умолчанию он только читает IORegistry и Core Audio inventory.
Режим cached descriptors не открывает устройство, а получает копии дескрипторов
из macOS. Отдельный явный `--status` открывает только vendor interface 0,
не захватывая её у другого драйвера, и отправляет пять разрешённых IN-запросов.
Если интерфейс занят/недоступен, программа сообщает ошибку, не меняет конфигурацию.
При нескольких картах требуется выбрать location. Серийный номер не запрашивается.

Офлайн-декодеры отвергают повреждённые USB-дескрипторы и vendor replies. Отдельный
`tools/analyze_init.py` разбирает формат APLO2 из upstream: события control/bulk,
переходы команд через границы кадров и отдельные streams по flags. Он печатает
только метаданные и SHA-256, не содержимое DSP-модулей, и вообще не умеет подключаться
к USB или воспроизводить последовательность. Формат APLO2 не содержит VID/PID и
версии firmware: успешный разбор **не подтверждает** принадлежность Twin X или
безопасность воспроизведения. Реальный capture пока отсутствует.

## Выбор дальнейшей архитектуры

| Путь | Оценка |
| --- | --- |
| Правильный model-specific init + штатный Apple USB Audio | Самый короткий возможный путь, если реальные дескрипторы и UAC2 clock-запросы совместимы с Apple. Пока неизвестно; в Linux понадобились обходы GET_RANGE, feedback и interface close. |
| IOUSBLib USB-транспорт + AudioServerPlugIn | Возможен как исследовательское направление; нужно отдельно доказать стабильное изохронное расписание и владение интерфейсами. TN3190 описывает необходимость dext для подавления Apple USB Audio в соответствующей конфигурации. Одного HAL-плагина недостаточно. |
| USBDriverKit + AudioDriverKit | Предпочтительный долгосрочный путь своего аппаратного драйвера: поддерживаемая Apple связка USB и Core Audio в userspace. Нужны Apple Developer provisioning/entitlements, активация dext и отдельное согласование установки. |

Сейчас выбран **IOUSBLib только для исследования**, а для полного собственного
аудиодрайвера — USBDriverKit + AudioDriverKit после подтверждения протокола.
Сборка Linux snd-usb-audio, ALSA, udev, systemd и PipeWire для macOS не подходит.
Переносимы факты протокола, проверка ответов и анализ кадров; USB API, изохронный
планировщик, буферы/clock и интеграция Core Audio требуют реализации для macOS.
Фиктивное HAL-устройство, генерирующее тишину, не создаётся.

UA Connect и официальный UAD Console не являются критерием готовности нашего USB-
транспорта: их совместимость не установлена, и наличие Core Audio-устройства её
не гарантирует. Console/UAD plug-ins остаются за пределами текущего этапа.

## Проверка и пределы

- В Linux-облаке собраны portable library и CLI; пройдены unit/CLI-тесты и
  проверка обработки malformed inputs. Они используют явно синтетические данные.
- GitHub Actions собирает **настоящий** IOKit backend в macOS и проверяет запуск
  inventory без Apollo. Результаты каждого commit доступны во вкладке Actions.
- Обнаружение loader и чтение cached descriptors на M5: **наблюдались у владельца**
  по скриншотам его запусков. В облаке карты нет; runtime PID не наблюдался.
- Vendor status на Twin X: **не проверен**.
- Firmware boot: подготовлен отдельный opt-in RAM загрузчик с закреплённым
  Twin X image, checksum/hash gate, readback и проверкой runtime. Он **не запускался
  на карте**, согласия на запись нет. [Код/план/ограничения](BOOT_EXPERIMENT.md).
- DSP initialization: **не реализована**, подтверждённой последовательности Twin X нет.
- Изохронное воспроизведение/запись, Core Audio device registration: **не реализованы**.
- Никакая успешная сборка, найденный PID или тестовая фикстура не считаются звуком.

## Штатные дополнительные сведения без изменения устройства

Обнаружение и cached descriptors уже получены. Для уточнения скорости владелец
может открыть ** → Об этом Mac → Подробнее → Отчёт о системе → USB**. Серийный
номер перед отправкой можно закрыть.

Если удобнее Terminal, встроенные команды только печатают результат, не создавая
файлов (это инструкции на будущее, агент их на Mac не выполнял):

```sh
sw_vers
uname -m
system_profiler SPUSBDataType
xcode-select -p
```

Не публикуйте полный отчёт с серийниками других устройств; достаточно блока Apollo.
Отсутствие Command Line Tools не требует сейчас их устанавливать — облачная сборка
уже готова. Повторно скачивать утилиту для фиксации полученного результата не нужно.

Карта наблюдается в loader 000E: не загружать firmware автоматически. Boot image
получен из собственной Windows-установки владельца, офлайн checksum/hash/layout
проверены. Подготовлены отдельный загрузчик, точная операция и план восстановления;
требуются проверки новой macOS-сборки и отдельное согласие на hardware-запуск.
Если после отдельно согласованного эксперимента видна runtime 000F,
следующий шаг — cached descriptors, затем отдельно известные IN-запросы. Если понадобится
полный init, нужен capture Windows-драйвера именно Twin X с зафиксированными firmware/
DSP hashes. Публиковать такой capture в открытом репозитории нельзя: он может содержать
ресурсы UA. Здесь нет загрузки ресурсов из сторонних источников.

Выполненные owner-тесты apollo-inspect не меняли firmware, DSP, clock, routing или
настройки macOS; системных установок проекта не было. Новый apollo-boot способен
менять RAM только в явно подтверждённом режиме. Его последствия и ограничения
восстановления описаны отдельно, а не заменены обещанием отсутствия риска.
